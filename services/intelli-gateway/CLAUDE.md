# intelli-gateway

The AI helper for site engineers: Claude answers questions about a generation site using
read-only tools. It is a hand-written tool-use loop with no agent frameworks. The tool layer is
MCP-ready.

**Owns:**
- the Claude integration (`services/claude/client.py`)
- the agent loop and conversation history
- the tool layer and its authorization
- engineer-written knowledge: point guides (meaning, limits, and per state, alarm bit or vendor
  fault code: message, severity, causes, checks, safety note), manuals, IM scripts and
  experience notes. In memory for now, its own Postgres later. Guides are keyed per site device.
- the HTTP API under `/api/v1`

**Does NOT own** (it reads them over the network, next step):
- site, device, point, reading and alarm data, which belong to backend-ot. Every backend-ot call
  will go in one package, `services/backend_ot/` (planned, not built yet); nothing else may
  talk to backend-ot.
- writes to plant systems: every tool is read-only, and no tool executes anything

## Commands
Run from the repo root as `make -C services/intelli-gateway <target>` (or `make <target>` here).
Recipes run in Git for Windows' sh. `make help` lists every target.
- **Setup:** `make install` runs uv sync into `.venv`. Add dependencies with `uv add` /
  `uv add --dev`, but ask the user first.
- **Checks:**
  - `make lint` (ruff, blocking) · `make format`
  - `make typecheck` (pyright; strict everywhere except `api/`, `fake_data/`, `knowledge/`,
    `prompts/`)
  - `make test` (pytest, no Docker, fake data, scripted LLM)
- **`make test-integration`:** calls the real Claude API, which costs tokens. It needs
  `ANTHROPIC_API_KEY`, and the test is skipped unless `RUN_LLM_TESTS=1` (the target sets it).
- **`make run`:** the API on the host at http://127.0.0.1:8030.
- **Running it:** development normally uses the whole platform via `make up` at the repo root.
  `make up` / `down` / `logs` here run the service alone on host port `INTELLI_GATEWAY_HTTP_PORT`
  (8030), and refuse while the root dev stack runs.

## Contracts
- **Provides:** `contracts/openapi/intelli-gateway.openapi.json`, generated by `make contract`.
  `tests/test_contract.py` fails while it is stale. The version is `API_VERSION` in `src/intelli_gateway/app.py`.
- **Consumes:** nothing in phase 1. In phase 2 it consumes `contracts/openapi/backend-ot.openapi.json`
  through strict response models. It never imports backend-ot code.

## Rules (from the design; don't change them without asking)
- **Layout (same as backend-ot):** Pydantic models only in `schemas/`, Protocols only in
  `interfaces/`, external clients only in `services/<system>/`, routers only in `api/routers/`,
  logging and exceptions in `utils/`, everything fake in `fake_data/`. Feature folders (`agent/`,
  `tools/`, `knowledge/`, `prompts/`) hold functions only.
- **Claude client:** only `services/claude/client.py` imports `anthropic`. The model, effort and
  limits come from `config.py`, never hard-coded elsewhere.
- **Agent loop:** the loop talks to tools only through `ToolProvider` (`list_tools` /
  `call_tool`). Never call tool functions directly.
- **Tools:**
  - nothing in `tools/` imports FastAPI, request objects or module-level state
  - a tool gets its validated input and a `RequestContext`; the site comes from the context,
    never from arguments
  - every call goes through `tools/authz.check`
  - expected failures raise `ToolError(error, hint)`; the provider turns every error into a
    result and never raises to the loop
  - outputs are bounded: row limits, summarized history, truncated text
- **Read-only:**
  - no raw-SQL tool and no write tool
  - a future action tool needs explicit human approval; don't build one in v1
- **Keep the three MCP concepts separate:** `tools/` (tools), `knowledge/` (resources),
  `prompts/` (prompts).
- **No frameworks:** no LangChain/LangGraph, vector DB, MCP server or queue unless asked.
- **No real plant data** in the repo. Fake data is Pydantic objects in `fake_data/`.

## Gotchas
- **Prompt cache order:** tools (sorted), then the static system block, then the site block
  (`cache_control`), then messages. Anything that varies per request (the current time, ids)
  goes in the user turn, never in the system prompt. Check `usage.cache_read_input_tokens`.
- **History is append-only:**
  - assistant content is stored exactly as returned (thinking blocks included), and earlier
    turns are never edited
  - a stopped run (timeout, max iterations) closes dangling `tool_use` blocks with error results
  - the next question extends a trailing user turn rather than adding a second one
- **Refusal fallback:** `fallbacks: "default"` is Claude API only. On Bedrock, Vertex or
  Foundry, switch to the SDK's client-side middleware in `services/claude/client.py`. After a mid-output
  fallback, `echo_content` drops the declined model's non-text blocks before the marker.
- **Missing credentials** surface as a 503 on the first `/ask` (the SDK raises `TypeError`),
  not at startup.
- **Fake data is a plant model** (`fake_data/site_data.py::PlantModel`): derived points read other
  points (INV2 status from cabinet temperature, POI = sum). Tests assert on its values at
  `tests/fakes.py::FIXED_NOW`, so changing a signal can move many tests.
- **Conversations are in memory** and process-local. Concurrent requests on the same
  conversation are not serialized (v1).
